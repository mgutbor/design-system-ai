# ADR-005: `apps/api` como proxy de IA (Hono) — deployment decision separable

- **Estado**: Aceptado (SPEC v3) · actualizado F7
- **Fecha**: 2026-08

> **Nota de reconciliación (2026-08)**: `apps/api` es contenido de la **F5
> original** (SPEC §11: "`apps/api` · UI del asistente"). Su implementación se
> completó en la fase de trabajo denominada F7; esta fase no es funcionalidad
> nueva fuera del roadmap, sino la parte de F5 que quedaba pendiente (ver
> SPEC §11 reconciliado).

## Contexto

La API key del proveedor LLM nunca debe estar en el navegador. Se necesita un backend mínimo que valide la petición, llame al proveedor y devuelva la respuesta. La plataforma de despliegue no debe condicionar la arquitectura.

## Decisión

`apps/api` como aplicación **Hono** con entrypoints aislados por plataforma:

```
apps/api/src/
├─ app.ts          # negocio: validación, errores, llamada a AI Core
└─ entrypoints/    # node.ts (local) · vercel.ts · cloudflare.ts (futuro)
```

Responsabilidades exactas (y solo estas): recibir la pregunta, validar, llamar a `answerQuestion` (AI Core), mapear errores (`{ error: { code, message, requestId } }`), devolver el `AIAnswer`. **No conoce el modelo de documentación ni implementa retrieval ni prompt building** (no importa `knowledge`; todo lo hace AI Core).

Contrato (F7, actualizado):

- `POST /api/ask` `{ question }` → `AIAnswer` (`answer`, `referencedComponents`, `confidence`, `hasRelevantContext`, `providerId`, `model`, `retrieval`) + `requestId` · 400/429/502/503/500.
- `GET /api/health` (nunca expone la key).

> **Actualización F7**: el contrato original de este ADR era `POST /api/chat { messages }` → `{ content, model, provider, usage, requestId }`, diseñado cuando el retrieval vivía en el navegador (SPEC §7 pre-F6). F6 movió la orquestación completa (retrieval → gate → context → prompt → provider) a AI Core (`answerQuestion`), así que la API ya no recibe mensajes grounded del cliente: recibe una pregunta y devuelve la respuesta estructurada. El resto del ADR (Hono, entrypoints, sin `knowledge`, mapeo de errores, deployment separable) se mantiene.

## Alternativas consideradas

- **Llamada directa desde el navegador**: filtra la API key — rechazada.
- **Express/Fastify**: más pesados; Hono corre en Node, Vercel, Netlify y Cloudflare Workers con el mismo código.
- **Vercel Function dentro de apps/docs**: viable, pero un app separado mantiene el contrato HTTP testable.

## Consecuencias

- La elección de plataforma es una **deployment decision** (recomendación: Vercel o Netlify, una sola plataforma para estática + funciones), no una dependencia arquitectónica: cambiar de plataforma solo toca el entrypoint.
- Cambiar de proveedor = cambiar `AI_PROVIDER`/variables en `apps/api`; el port `AIProvider` y AI Core no cambian.
- **CORS implementado en F5** (UI del asistente en `apps/docs`): `Access-Control-Allow-Origin: *`, sin credenciales, preflight OPTIONS → 204 — API pública de documentación.
- Rate limiting, autenticación de usuario y streaming SSE quedan fuera (deuda documentada en `docs/api.md`).
