# ADR-006: Fuente única de documentación (Storybook + docs app + playground)

- **Estado**: Aceptado (SPEC v3, actualizado en V1-0)
- **Fecha**: 2026-08

## Contexto

Se necesita documentación de producto sin duplicar contenido entre Storybook y la docs app. El contenido se escribe una vez; las superficies lo renderizan.

## Decisión

El **contenido vive en la carpeta del paquete** y fluye hacia la metadata JSON generada, que es el **contrato de datos único** que consumen la docs app y knowledge:

- **Prosa de guía** (descripción, tags, `a11ySummary`, variantes, tamaños, **cuándo usar / cuándo NO usar**, comportamiento): `COMPONENT_DESCRIPTORS` en `packages/react/src/metadata/metadata.ts`.
- **Ejemplos canónicos**: `*.examples.tsx` (único lugar con código de ejemplo).
- **Props**: generadas de los tipos (react-docgen-typescript).
- **Tokens**: generados del JSON fuente de `@ods-ai/tokens`.

El generador (`src/metadata/metadata.ts`) emite la metadata JSON a `dist/metadata/`; la docs app y knowledge la consumen. **No existe MDX en el proyecto desde V1-0.**

| Superficie        | Responsabilidad                                                                       | No hace                                             |
| ----------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **Storybook**     | Entorno de desarrollo: playground, revisión visual, addon-a11y, interaction tests     | No es el sitio público; no redacta contenido propio |
| **docs app** (F4) | Producto público: páginas por componente, tokens, guidelines, AI Assistant, copy-code | No reescribe contenido                              |

**Reglas anti-duplicación:**

1. `*.examples.tsx` es el único lugar con ejemplos (`{ code, render }`); lo importan stories y docs app.
2. Tablas de props generadas de los tipos (react-docgen-typescript).
3. La guía de uso por componente (cuándo usar / cuándo NO usar / comportamiento) se redacta en `COMPONENT_DESCRIPTORS` y se emite a la metadata; la docs app la renderiza en la ficha.
4. Tablas de tokens generadas del JSON fuente.
5. Metadata JSON generada alimenta docs app + índice de knowledge.

**Playground** (F4): aplicación de referencia que consume solo el DS y documenta _gaps_ de composición → alimenta el roadmap.

## Decisión V1-0 (2026-08): fin de los `*.docs.mdx`

Los 8 `*.docs.mdx` eran huérfanos (ni Storybook ni la docs app los consumían) y duplicaban parcialmente la metadata (tablas de API, ejemplos, a11y). En V1-0 se resolvió:

1. **Contenido único migrado a `COMPONENT_DESCRIPTORS`** → metadata JSON:
   - `whenToUse` / `whenNotToUse` (guía de decisión; Button y Spinner tenían contenido en MDX, el resto se derivó del comportamiento real de los componentes).
   - `behavior` (comportamiento no evidente desde la API: Modal focus/backdrop, FormField cableado ARIA, estados de Input/Select/Checkbox).
2. **Contenido redundante descartado** (tablas de API y ejemplos ya vivían en metadata/examples; a11y queda cubierto por `a11ySummary`).
3. **Archivos eliminados**; la estructura por componente ya no incluye `*.docs.mdx`.

**Consecuencia**: una sola fuente de verdad (metadata JSON); sin capa MDX; la docs app renderiza la guía completa desde la metadata. Si en el futuro se necesitara MDX (p. ej. guías largas), se reintroduciría con su propio ADR — no se prevé para v1.

## Diferimientos (ajuste v3)

- **Metadata freshness check en CI**: diferido hasta que exista suficiente contenido para justificarlo.
- Storybook-only como sitio público es el plan B aceptable (perdería AI Assistant y páginas de producto).
