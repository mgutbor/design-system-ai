# ADR-007: APIs de componentes deliberadamente pequeñas

- **Estado**: Aceptado (SPEC v3)
- **Fecha**: 2026-08

## Contexto

Una API pública grande es deuda: cada prop extra es superficie de testeo, documentación y mantenimiento. La tendencia a añadir props "por si acaso" debe contrarrestarse con una regla explícita.

## Decisión

La API pública de cada componente es la **API nativa extendida con lo estrictamente necesario**. En v1:

- **Sin polimorfismo** (`as?: ElementType` eliminado de Button): si el playground necesita un "Button que navega", se resuelve en la aplicación (link estilizado), no en el DS.
- **Sin props de layout** (`fullWidth` eliminado): el layout es responsabilidad del consumidor (CSS); se añadirá en v2 solo con un caso de uso real documentado.
- Regla: una prop solo entra en v1 si responde a una necesidad demostrada por un componente del DS o un patrón real de la aplicación de referencia.

API final de Button (v1):

```ts
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: 'primary' | 'secondary' | 'ghost' | 'destructive' // default 'primary'
  size?: 'sm' | 'md' | 'lg' // default 'md'
  loading?: boolean // default false
}
```

## Alternativas consideradas

- Button polimórfico (`as`): potente pero multiplica testing, tipado y accesibilidad (roles cambiantes). Diferido con caso real.
- `fullWidth`: cómodo pero acopla layout a la semántica del componente.

## Consecuencias

- Menos superficie de testeo y documentación; decisiones de composición explícitas en el consumidor.
