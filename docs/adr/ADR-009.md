# ADR-009: Playground como Reference Application (no producto sanitario)

- **Estado**: Aceptado (SPEC v3)
- **Fecha**: 2026-08

## Contexto

Una aplicación de ejemplo demuestra que el DS construye aplicaciones reales, pero puede convertirse en un segundo producto (scope creep). El dominio "Healthcare Patient Portal" es piel de demostración, no un producto.

## Decisión

`apps/playground` es un **showcase de composición** que consume exclusivamente `packages/react` + `packages/tokens`. Límites duros:

1. **Cero lógica de dominio**: sin motor de citas, sin auth, sin backend, sin persistencia.
2. **Cero componentes de dominio**: cada elemento UI es un componente del DS o el shell de composición (layout + navegación).
3. **Datos 100% ficticios** en un único fixture, con disclaimer visible.
4. **Alcance**: 1 layout responsive + ≤4 páginas (Dashboard, Citas, Perfil, Estados).
5. **Registro de gaps**: cualquier patrón no cubierto por el DS se documenta como gap (componer con primitivas o proponer componente nuevo) → alimenta el roadmap.

## Alternativas consideradas

- Playground completo tipo producto: más impresionante, pero duplica el mantenimiento — rechazado.
- Sin playground: el DS queda sin demostración de composición real — rechazado.

## Consecuencias

- El criterio de éxito es "el DS cubre una superficie de app real", no "es un portal sanitario".
- El playground es también el target de pruebas E2E de composición (F6).
